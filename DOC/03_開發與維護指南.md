# 開發與維護指南

## npm scripts 全表

```bash
npm install               # 安裝依賴
npm run dev                # vite dev server,只給 popup/主 HTML 用,不是完整擴充功能
npm run build               # 完整擴充功能建置到 dist/(popup 走 vite + content/background 走 esbuild + 複製 public/)
npm run build:zip           # build 後另外打包 zip/NHITW_cloud_analyzer_v<version>_<date>.zip
npm run build:alpha         # 同 build:zip,但標記為 ALPHA
npm test                    # Vitest 單元測試(headless,node + jsdom)
npm run test:watch          # Vitest watch 模式
npm run test:manual         # 以 TEST 模式建置(manifest 加入 http://localhost/* host permission)後啟動 tests/serve.js
npm run lint                 # ESLint
npm run lint:fix             # ESLint 自動修復
npm run type-check           # tsc -p jsconfig.json --noEmit(型別安全網,不編譯、無 runtime 影響)
```

## Build pipeline(非顯而易見之處)

`npm run build` = `vite build && node scripts/build.js`,兩階段缺一不可、順序不能顛倒:

1. `vite build`(設定檔 `vite.config.js`)把 `index.html` + `src/popup.jsx` 建到 `dist/`。**只**服務擴充功能 popup 與獨立 HTML 入口,**不**處理 content script。
2. `node scripts/build.js` 直接用 **esbuild**(不經過 Vite/Rollup)把 `src/contentScript.jsx` → `dist/content.js`、`src/background.js` → `dist/background.js` 打包成 IIFE,然後複製 `public/manifest.json` 與 `public/images/` 到 `dist/`。

**後果**:content script 與 background service worker 不走 Vite/Rollup。任何 Vite-specific 語法(如 `import.meta.glob`、Vite plugin)在 `contentScript.jsx`/`background.js` 內都不會生效。

`scripts/build.js --test`(即 `npm run test:manual` 內部呼叫)額外把 `dist/manifest.json` 的 host permissions 與 content script matches 加入 `http://localhost/*`,並開啟 sourcemap。**這個 test-patched manifest 不可提交進版控。**

## 測試策略

- **框架**:Vitest headless(`node` + `jsdom` 環境),設定檔 `vitest.config.js`。無需開瀏覽器即可在 CI 跑。
- **測試檔慣例**:
  - `tests/test_*.js` —— processor 純函數測試(如 `test_medicationProcessor.js`、`test_labProcessor.js`、`test_authorization.js`、`test_responseNormalizer.js`)。
  - `tests/*.test.{js,jsx}` —— util 與 React hook 測試(如 `settingsManager.test.js`、`useNhiDataState.test.jsx`、`SettingsContext.test.jsx`)。
  - 兩種 glob 都被 `vitest.config.js#test.include` 收錄。
- **chrome stub**:`tests/vitest.setup.js` 提供 `chrome.*` API 的最小 stub,測試檔不用另外 mock 整個 chrome namespace。
- **執行單一檔案**:`npx vitest run tests/test_labProcessor.js`。
- **手動測試流程**(`npm run test:manual`):建置 TEST 模式擴充功能 → `node tests/serve.js` 起本機 server → Chrome 以「載入未封裝擴充功能」載入 `dist/` → 造訪 `http://localhost:5173/` → 用 popup 的「載入本地資料」上傳 `tests/test_data/` 內的 JSON 做端對端驗證 → 改完程式碼要重新 `npm run test:manual` 再重新整理頁面(esbuild/vite 都不是 watch 模式)。

當前基準(2026-07-05,`dev-techdebt-features` 分支):29 個測試檔、262 個測試全綠。

- **時區前提**:測試假設 `TZ=Asia/Taipei`(本專案服務台灣健保雲端)。
  `chineseMedProcessor.calculateRemainingDays` 的午夜界線計算依本地時區,在 UTC 環境會有
  1 個測試失敗(本地可用 `TZ=UTC npm test` 重現);CI 已明訂 TZ,本機在台灣時區不受影響。
- **characterization 測試慣例**(issue #68 第 4 點紀律):重構已有測試覆蓋的核心模組
  (processor、settingsManager 等)前,先對「現行行為」補測試並確認全綠,再動架構;
  重構期間既有測試只能加不能改斷言。範例見 `tests/settingsManager.test.js` 的
  loadAllSettings characterization 區塊與 `tests/fixtures/storageKeys.js` 快照。

## Lint 政策

- 設定檔:`eslint.config.js`(ESLint flat config),含 `@stylistic/eslint-plugin` 客製化風格規則 + React/React Hooks 規則。`react/prop-types` 已明確關閉(JS 專案不用 PropTypes,型別由 `npm run type-check` 把關)。
- **驗證標準是「0 errors」**(issue #68 第 1 點處理後已全數清零):修改程式碼後 `npm run lint` 不得出現任何 error;CI(`.github/workflows/ci.yml`)會在 push/PR 時強制執行 lint + type-check + test + build。warnings 目前保留 23 個(`react-refresh/only-export-components` 15、`react-hooks/exhaustive-deps` 8,修復涉及行為變更,另案處理),不應新增。
- **`no-console`**:已啟用(允許 `warn`/`error`),`src/` 下目前為 0 未歸零問題;新程式碼避免加入未受控的 `console.log`(改用 `src/utils/logger.js` 的 `debugLog`,預設靜默,使用者在 console 執行 `localStorage.setItem('nhitw_debug','1')` 後重新整理才會輸出)。
- **`no-undef`**:`src/` 下目前為 0,必須維持(這是真實的 ReferenceError 風險指標,不是風格問題,新程式碼不可讓此規則計數回升)。
- 注意:`npx eslint`(不帶路徑)預設也會掃到 gitignored 的 `.test_data/` 等本機暫存目錄,問題數會比 `npx eslint src` 高;衡量「本次修改有沒有新增 lint 債」請以 `src/` 範圍為準。

## CI 與相容性政策

- **CI**(`.github/workflows/ci.yml`,2026-07-04 新增):push/PR 自動跑
  `npm ci → lint → type-check → test → build`,任一失敗即紅燈。
  `package-lock.json` 已入版控(2026-07-04 起,原本在 .gitignore)——**升級依賴後
  記得連同 lockfile 一起 commit**,否則 CI 的 `npm ci` 會因不同步而失敗。
- **瀏覽器底線 Chrome 109**(issue #68 第 2 點):三處必須同步——
  `public/manifest.json#minimum_chrome_version`、`vite.config.js#build.target`、
  `scripts/build.js` 兩處 esbuild `target`。目前皆為 109(Win7/8.1 的 Chrome 最終版,
  即「院所老電腦」天花板)。這只保證**語法層**;runtime 驗證方式見維護者本機
  `.test_data/chrome109-testing.md`(gitignored)。
- Release 用的 `.github/workflows/release.yml` 與 CI 互相獨立,互不影響。

## 常見任務 how-to

### 新增資料型別

**2026-07-07 起**:方向一(`DOC/07_擴充藍圖.md`)舊 14 型別遷入 registry 已完成,
`DATA_TYPES`/`API_PATH_MAP`/`NODE_TO_DATA_TYPE`/`TYPE_SHAPE`/抓取分流/`buildShareData`/
`LOCAL_KEY_TO_STORE_TYPE` 等分散登記全數改為由描述檔衍生,不再逐檔手寫。新增資料型別
只需兩步:

1. **加一行描述**:核心型別(有專屬 tab/UI 消費)加進 `src/dataTypes/coreTypes.js` 的
   `CORE_DATA_TYPES`;開發者「完整抓取模式」補抓型別加進 `src/dataTypes/devTypes.js` 的
   `DEV_DATA_TYPES`。欄位:`key`(store/匯出/匯入全系統唯一字串)、`node`(JWT Permission
   節點,免授權檢查則省略)、`apiPath`、`shape`(responseNormalizer 形狀,省略 = `'rows'`)、
   `exportKey`(對外契約/下載 JSON/本地匯入用別名,省略 = 與 `key` 相同)、`fetchGroup`
   (`'special'` 走 special 批次,省略 = regular)、`cloudSettingKey`(special 型別的抓取開關)。
   加好之後 `src/dataTypes/registry.js` 會自動衍生所有既有接點,不需要再手動改
   `apiPathMap.js`/`permissionMap.js`/`responseNormalizer.js`/`nhitwExport.js`/
   `localDataHandler.js`。
2. **若要顯示於 UI**(方向二/四待收斂的範圍,目前仍是手寫樣板):在 `src/utils/` 新建
   `<type>Processor.js`(singleton + `process<Type>Data(raw, settings)`),然後在
   `src/utils/dataManager.js` 的 `PROCESSOR_REGISTRY` 加一筆項目(`{ sourceKey, guard, run,
   setterName, resultKey }`),並在 `collectDataSources()` 補上對應的 `dataStore.getData(...)`
   讀取。也別忘了在 `src/hooks/useNhiDataState.js` 新增對應 React state 與 setter,並在需要
   顯示的地方(`FloatingIcon.jsx`/`Overview.jsx`/新 tab 元件)接線。**新增 tab 時**:在
   `src/components/tabs/tabIds.js` 的 `TAB` 加一個穩定字串 id,`MainDialogHeader` 的
   `<Tab value={TAB.x}>` 與 `FloatingIcon` 的 `<TabPanel index={TAB.x}>` 都用該
   id——**禁止用數字 index**(2026-07-05 起,見 `DOC/07` 方向三)。

### 新增設定(chrome.storage.sync)

完整說明見 [`Settings.md`](./Settings.md)。摘要:

1. `src/config/defaultSettings.js` 在對應 section 加一行預設值(storage 鍵自動同名,由 `settingsSchema.js` 衍生,**不需**再改 `settingsManager.js`)。
2. `src/components/settings/` 下對應分類元件加 UI 控制項(如西藥設定加在 `MedicationSettings.jsx`)。
3. 若此設定會被 processor 讀取,經 `dataManager.js` 呼叫 `process<Type>Data` 時的 `settings` 參數傳入(不要用 `window.*` 側通道——階段 5 已把 `medicationFormatSettings` 這類側通道全部移除)。

### 新增複製格式元素

西藥/檢驗共用 `src/components/tabs/copyFormat/` 的通用編輯器,差異點都在 config 檔:

- 西藥元素/預設值/storage key:`src/components/tabs/copyFormat/medicationConfig.jsx`
- 檢驗元素/預設值/storage key:`src/components/tabs/copyFormat/labConfig.jsx`

**只改對應 config,不要改 `FormatElementsPanel.jsx`/`useFormatEditorState.js`/`FormatPreview.jsx`/`dragDropHandlers.js` 這四個通用模組**(除非新元素需要通用行為本身的變更,例如新的拖曳互動)。若要新增第三種可複製資料型別(例如未來的中藥自訂格式),仿照現有兩個 config 的介面新建一個 config 檔,並在對應的 editor 元件(如 `MedicationCustomFormatEditor.jsx`/`LabCustomFormatEditor.jsx` 的同層新檔)接入通用模組。

## Release 流程

- Release 由 GitHub Actions workflow `.github/workflows/release.yml` 觸發,手動 `workflow_dispatch`(可選 pre-release flag 與 message)。流程:`npm install && npm run build` → 打 tag `v<version>-<YYYYMMDD>` → 把 `dist/` 打包成 zip → 發布 GitHub release。
- `release-stable.sh` / `release-alpha.sh` 是給維護者用的便利腳本(bash,Unix shell):互動詢問是否更新 `package.json#version`,然後把目前分支合併進 `release` 分支並 push——push 這個動作才會觸發 release build。這兩個腳本用 bash 特有語法(`sed`/`awk`/互動 `read`),在 PowerShell 環境無法直接執行,需要 Git Bash / WSL / 其他 POSIX shell。
