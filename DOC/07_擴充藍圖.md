## 現狀盤點:新增一個資料型別要碰的接點

六階段重構後,各接點都已是「宣告式一行」,問題不在行數,在**分散**與**命名漂移**:

| # | 檔案 | 要加什麼 | 性質 |
|---|------|----------|------|
| 1 | `store/dataStore.js#DATA_TYPES` | 型別字串 | 一行 |
| 2 | `apiInterceptor/apiPathMap.js` | `[型別, 'imueXXXX/.../get-data']` | 一行 |
| 3 | `apiInterceptor/permissionMap.js` | JWT 節點 → 型別(若需授權) | 一行 |
| 4 | `apiInterceptor/index.js` | 加入 `regularTypes` 或 `specialTypes` | 一行 |
| 5 | `apiInterceptor/responseNormalizer.js` | 回應形狀特殊時加分支 | **if-else 累積點** |
| 6 | `utils/<type>Processor.js` + `dataManager.js#PROCESSOR_REGISTRY` | processor + 註冊項 | 新檔 + 一項 |
| 7 | `hooks/useNhiDataState.js` | useState + setter 對照 | **手寫樣板累積點** |
| 8 | tab 元件 + `FloatingIcon.jsx` | `<TabPanel index={N}>` | **數字 index 地雷** |
| 9 | `store/nhitwExport.js#buildShareData` | 對外契約 key | 一行(契約) |
| 10 | `localDataHandler.js#LOCAL_KEY_TO_STORE_TYPE` | 本地匯入 key | 一行 |

## 已知地雷(unknown unknown 的主要來源)

1. **命名漂移**:同一份資料有三個名字——store 內 `labdata`、dataManager 的
   `dataSources.labData`、對外契約 `lab`;`patientsummary` vs `patientSummary`
   的大小寫不一致已產生過真實 bug(`dataManager.js` 的 patientSummary guard
   有一段大小寫 fallback 補丁)。**每個新型別若不明訂命名,就會再生一組別名**。
2. **Tab 以數字 index 定位**:`FloatingIcon.jsx` 的 `<TabPanel index={0..6}>`、
   `useSettingsState.js` 訊息處理中的 `tabIndex: 9/10` 魔術數字。插入一個 tab
   會使後面全部位移,而且訊息端不會有編譯錯誤,只會默默開錯頁。
3. **`useNhiDataState` 樣板**:14 個型別 × (useState + setter 註冊),
   純機械但每次都要手寫。
4. **`responseNormalizer` 特例分支**:目前 5 個 if,每個回應形狀特殊的新 API
   都會再加一個。

## 方向一:資料型別描述檔(核心建議,新型別的目標形態)

一個型別 = 一個描述檔,集中回答「這份資料是什麼」的所有問題;
上表 1–5、9、10 全部由 registry 衍生,不再逐檔登記。

```js
// src/dataTypes/vaccination.js(示意——尚未實作)
export default {
  key: 'vaccination',              // 唯一識別,camelCase,全系統只用這個名字
  apiPath: 'imueXXXX/imueXXXXsYY/get-data',
  permissionNode: 'XXX',           // 無需授權檢查則省略
  fetchKind: 'regular',            // 'regular' | 'special'(對齊 index.js 現有分流)
  responseShape: 'rows',           // 'rows' | 'single' | 'wrapped'(取代 normalizer if-else)
  exportKey: 'vaccination',        // NHITW_DATA 對外契約 key(⚠️ 一經發布不可改)
  localImportKey: 'vaccinationData', // 本地 JSON 匯入 key;不支援則省略
  process: (raw, settings) => ..., // 或 import 自 utils/vaccinationProcessor.js
  ui: {
    surface: 'tab',                // 'tab' | 'overview-card' | 'popup' | 'none'
    tabId: 'vaccination',          // 穩定字串 id(見方向三)
  },
};
```

```js
// src/dataTypes/registry.js(示意)——衍生所有既有消費點
import vaccination from './vaccination';
export const TYPE_REGISTRY = [vaccination /* , ... */];
export const API_PATH_MAP   = new Map(TYPE_REGISTRY.map(t => [t.key, t.apiPath]));
export const DATA_TYPES     = TYPE_REGISTRY.map(t => t.key);
export const buildShareData = () => Object.fromEntries(
  TYPE_REGISTRY.map(t => [t.exportKey, dataStore.getData(t.key)]));
// ...normalizer 依 responseShape 三選一,不再寫 if-else
```

**命名規則(立即生效,不等實作)**:
- 新型別的 `key` 一律 camelCase,store/processor/state/匯出全用同一字串;
  `exportKey` 只有在對外契約需要不同名時才明訂。
- 既有的 `labdata`/`patientsummary` 等歷史小寫**不改**(對外契約 + storage 相容),
  視同 settingsSchema 的 `LEGACY_STORAGE_KEYS`:封存,不再新增同類。

**遷移策略**:不做 big-bang。下一個新資料型別直接以描述檔形態實作(pilot,
registry 先只含新型別,與既有 7 檔登記並存);驗證順手後,舊型別依
「characterization 測試先行」的紀律逐一搬入(每型別一個小 commit),
搬完才刪除舊的分散登記。

## 方向二:表格資料的標準處理管線

觀察:NHI 的資料絕大多數是同一形狀——**rows → 欄位正規化 → 依「日期+院所」
分組 → 日期新到舊排序 → 表格呈現**。現有 12 個 processor 各自把這條管線
寫一遍,只有中段的欄位邏輯真正不同。

目標契約(已有基礎:`src/types/processors.js` 的 typedef + `PROCESSOR_REGISTRY`):

- **processor 統一簽名**:`process(raw, settings) → ViewModel`,ViewModel 型別
  寫進 `types/processors.js`。純函數、不碰 chrome API、不碰 DOM——這是可測試性的底線。
- **共用 toolkit**(尚未實作,從既有 processor 抽出而非重寫):
  `groupByVisit(rows, {dateField, hospField})`、`sortByDateDesc`、
  民國年/日期格式化(`ageUtils` 已是先例)。新 processor 用 toolkit 組裝,
  只寫自己的欄位邏輯。
- **config 驅動的通用表格 view**(仿 `copyFormat/` 的成功模式:通用引擎 + 每型別
  一個 config):新的表格型資料只需提供 columns config(欄名、取值、格式化、
  是否可複製),不再複製整個 tab 元件。`copyFormat/` 合併省了 1,693 行,
  同樣的收斂在 tab 元件上還沒做。

新表格型資料的理想成本:**描述檔 + columns config + (必要時)專屬欄位邏輯**,約 2–3 個檔案。

## 方向三:UI 掛載點 registry(消滅數字 index)

- **tab registry**:每個 tab 一個穩定字串 id(`'overview'`、`'medication'`…),
  `FloatingIcon` 從 registry 生成 `<Tab>`/`<TabPanel>`,順序由陣列決定;
  跨元件/訊息一律用 id(`switchToTab('labCustomFormat')`),
  廢除 `tabIndex: 9/10` 這類魔術數字。
- **Overview 卡片 registry**:`Overview_*.jsx` 已是「一卡片一檔」的形態,
  差一個宣告式清單(id、顯示條件——例如綁哪個設定開關、資料來源)。
- **popup 設定區**:維持現狀(`PopupSettings` 的手動組裝),數量少、變動少,
  不值得 registry 化。

## 方向四:資料 → UI 的訂閱(endgame,已列於 Roadmap)

`dataStore.subscribe` 目前無消費者,UI 靠 `dataFetchCompleted` 事件全量重處理。
終局是 `useNhiData(typeKey)` hook:元件直接訂閱單一型別的 processed 結果,
`useNhiDataState` 的 14 組 useState/setter 樣板隨之消失。
**前置條件**:方向一的 registry 先就位(hook 需要知道每型別的 processor 與設定
依賴),且需驗證批次抓取時的 render 行為(`dataStore.js` 檔頭註解已預留)。

## 變數(設定)的處理

已解決,規則見 `Settings.md`。對新資料型別只補一條:**新型別的設定歸入
`defaultSettings.js` 既有 section**(顯示類→`general`、抓取開關→`cloud`、
資料處理→該型別所屬領域 section);只有當設定超過 3–4 個時才開新 section,
開新 section 不需要改 schema(自動衍生)。

## 新 API 資料的決策 checklist(動手前先回答)

1. **抓取**:哪個 imue endpoint?需要 JWT 授權節點嗎?regular 還是 special?
2. **形狀**:回應是 rows、單一物件、還是包裹形?(對應 `responseShape`)
3. **呈現**:獨立 tab、Overview 卡片、還是只進 popup?要不要設定開關(`cloud` section)?
4. **預處理**:純表格(用 toolkit + columns config)還是需要專屬邏輯(寫 processor)?
5. **契約**:要進 `NHITW_DATA` 嗎?`exportKey` 取名一次定終身。
6. **本地匯入**:要支援 JSON 匯入嗎?(`localImportKey`)
7. **測試**:processor 是純函數 → 先寫測試資料與預期輸出,再實作。

## 不變的底線(任何方向都不可違反)

- `NHITW_DATA` 對外契約(`02`):key 只增不改。
- processor 純函數、可在 vitest headless 環境執行。
- 設定單一事實來源(`Settings.md`)。
- CI 全綠 + 先測試後重構(`03`)。
