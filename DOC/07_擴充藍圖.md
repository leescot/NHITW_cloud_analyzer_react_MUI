2. ~~**Tab 以數字 index 定位**~~:*(2026-07-05 已處理:訊息端 `tabIndex` 魔術數字

## 方向一:資料型別描述檔(核心建議,新型別的目標形態)

一個型別 = 一個描述檔,集中回答「這份資料是什麼」的所有問題;
上表 1–5、9、10 全部由 registry 衍生,不再逐檔登記。

```js
// src/dataTypes/vaccination.js(示意——尚未實作)
export default {
  key: 'vaccination',              // 唯一識別,camelCase,全系統只用這個名字
  apiPath: 'imueXXXX/imueXXXXsYY/get-data',
  permissionNode: 'XXX',           // 無需授權檢查則省略
  fetchKind: 'regular',            // 'regular' | 'special'(對齊 index.js 現有分流)
  responseShape: 'rows',           // 'rows' | 'single' | 'wrapped'(取代 normalizer if-else)
  exportKey: 'vaccination',        // NHITW_DATA 對外契約 key(⚠️ 一經發布不可改)
  localImportKey: 'vaccinationData', // 本地 JSON 匯入 key;不支援則省略
  process: (raw, settings) => ..., // 或 import 自 utils/vaccinationProcessor.js
  ui: {
    surface: 'tab',                // 'tab' | 'overview-card' | 'popup' | 'none'
    tabId: 'vaccination',          // 穩定字串 id(見方向三)
  },
};
```

```js
// src/dataTypes/registry.js(示意)——衍生所有既有消費點
import vaccination from './vaccination';
export const TYPE_REGISTRY = [vaccination /* , ... */];
export const API_PATH_MAP   = new Map(TYPE_REGISTRY.map(t => [t.key, t.apiPath]));
export const DATA_TYPES     = TYPE_REGISTRY.map(t => t.key);
export const buildShareData = () => Object.fromEntries(
  TYPE_REGISTRY.map(t => [t.exportKey, dataStore.getData(t.key)]));
// ...normalizer 依 responseShape 三選一,不再寫 if-else
```

**命名規則(立即生效,不等實作)**:
- 新型別的 `key` 一律 camelCase,store/processor/state/匯出全用同一字串;
  `exportKey` 只有在對外契約需要不同名時才明訂。
- 既有的 `labdata`/`patientsummary` 等歷史小寫**不改**,視同 settingsSchema 的
  `LEGACY_STORAGE_KEYS`:封存,不再新增同類。*(2026-07-07 更新理由:`NHITW_DATA`
  對外契約已解凍(尚無消費端,見 DOC/02),不改名的真正原因是內部 store key 改名
  會波及所有 processor/元件/測試,且既有下載 JSON 與 `.test_data/` 測資會作廢——
  歷史包袱實際只有 `lab`↔`labdata`、`patientSummary`↔`patientsummary` 兩個 alias
  條目,留著幾乎零成本,划不來為此大改名。)*

**遷移策略**:不做 big-bang。下一個新資料型別直接以描述檔形態實作(pilot,
registry 先只含新型別,與既有 7 檔登記並存);驗證順手後,舊型別依
「characterization 測試先行」的紀律逐一搬入(每型別一個小 commit),
搬完才刪除舊的分散登記。
*(2026-07-07 決策:舊 14 型別遷入時 **key 一律照舊**(選項 A)——描述檔的
`exportKey`/`localImportKey` 欄位只有 `labdata`/`patientsummary` 需要明訂,
其餘同名省略;舊下載 JSON 與測資全程可用,零破壞。)*

## 方向二:表格資料的標準處理管線

觀察:NHI 的資料絕大多數是同一形狀——**rows → 欄位正規化 → 依「日期+院所」
分組 → 日期新到舊排序 → 表格呈現**。現有 12 個 processor 各自把這條管線
寫一遍,只有中段的欄位邏輯真正不同。

目標契約(已有基礎:`src/types/processors.js` 的 typedef + `PROCESSOR_REGISTRY`):

- **processor 統一簽名**:`process(raw, settings) → ViewModel`,ViewModel 型別
  寫進 `types/processors.js`。純函數、不碰 chrome API、不碰 DOM——這是可測試性的底線。
- **共用 toolkit**(尚未實作,從既有 processor 抽出而非重寫):
  `groupByVisit(rows, {dateField, hospField})`、`sortByDateDesc`、
  民國年/日期格式化(`ageUtils` 已是先例)。新 processor 用 toolkit 組裝,
  只寫自己的欄位邏輯。
- **config 驅動的通用表格 view**(仿 `copyFormat/` 的成功模式:通用引擎 + 每型別
  一個 config):新的表格型資料只需提供 columns config(欄名、取值、格式化、
  是否可複製),不再複製整個 tab 元件。`copyFormat/` 合併省了 1,693 行,
  同樣的收斂在 tab 元件上還沒做。

新表格型資料的理想成本:**描述檔 + columns config + (必要時)專屬欄位邏輯**,約 2–3 個檔案。

## 方向三:UI 掛載點 registry(消滅數字 index)

- **tab registry**:每個 tab 一個穩定字串 id,跨元件一律用 id,廢除數字 index。
  *(2026-07-05 已完成核心:`src/components/tabs/tabIds.js` 單一來源,
  `MainDialogHeader` 的 `<Tab value={TAB.x}>` 與 `FloatingIcon` 的
  `<TabPanel index={TAB.x}>` 全面字串化,行為測試 `tests/MainDialogHeader.test.jsx`。
  尚未做:從 registry 陣列「生成」`<Tab>`/`<TabPanel>`(label/icon/顏色/計數
  收斂為宣告),留待方向一/二的宣告式收斂一併處理。)*
- **Overview 卡片 registry**:`Overview_*.jsx` 已是「一卡片一檔」的形態,
  差一個宣告式清單(id、顯示條件——例如綁哪個設定開關、資料來源)。
- **popup 設定區**:維持現狀(`PopupSettings` 的手動組裝),數量少、變動少,
  不值得 registry 化。

## 方向四:資料 → UI 的訂閱(endgame,已列於 Roadmap)

`dataStore.subscribe` 目前無消費者,UI 靠 `dataFetchCompleted` 事件全量重處理。
終局是 `useNhiData(typeKey)` hook:元件直接訂閱單一型別的 processed 結果,
`useNhiDataState` 的 14 組 useState/setter 樣板隨之消失。
**前置條件**:方向一的 registry 先就位(hook 需要知道每型別的 processor 與設定
依賴),且需驗證批次抓取時的 render 行為(`dataStore.js` 檔頭註解已預留)。

## 方向五:使用者自訂代碼集與外部對照表(CodeSet)

> **驅動需求:issue #64、#65、#66、#67**(2026-07 使用者提出,方向與本節一致):
> - #64/#66/#67:檢驗與檢查/影像的關注項目要能自訂(CRUD、代碼、啟停、排序、還原預設),
>   動機是「各科有自己的重要項目」。
> - #66/#67 共同點出核心技術需求:**一對多代碼(alias)**——同一檢驗在不同院所
>   代碼可能不同(CBC、Cr/CCr、CRP/hs-CRP、尿蛋白)。
> - #65:儲存策略約束(見「儲存分層」小節,已納入)。
>
> 這三個功能 issue 就是 CodeSet 的第一個實戰目標(pilot),見文末執行順序。

### 現況盤點

「使用者自訂要顯示哪些代碼」這件事,今天已經以孤例形式存在,但各做各的:

| 自訂點 | 存放 | 編輯 UI |
|--------|------|---------|
| ATC5 分組 + 顏色(`atc5.groups`/`colorGroups`) | `chrome.storage.sync` | `MedicationSettings` 自帶 dialog |
| 關注檢驗/影像清單(`focusedLabTests`/`focusedImageTests`) | sync | `OverviewSettings` 自帶 dialog |
| 檢驗複製項目(`labChooseCopyItems`) | sync | `LabSettings` |

而**寫死在程式裡、使用者動不了**的內建對照表——正是未來開放自訂的候選:

| 內建表 | 位置 | 內容 |
|--------|------|------|
| 檢驗縮寫對照 | `utils/labProcessorModules/abbreviationUtils.js`(178 行) | orderCode/itemName → 縮寫 |
| 自訂參考值 | `utils/labProcessorModules/customReferenceRanges.js`(70 行) | orderCode → 參考範圍 |
| 預設檢驗/影像/ATC 清單 | `config/labTests.js`/`imageTests.js`/`medicationGroups.js` | 各清單的出廠預設 |

### 概念統一:代碼集(CodeSet)

把上述全部收斂成同一種東西:

```js
// 示意——每個代碼集一份宣告(config,不是元件)
{
  id: 'labFocus',                  // 唯一識別
  dataType: 'labdata',             // 適用的資料型別(與方向一的描述檔互相引用)
  shape: 'list',                   // 'list'(勾選清單)| 'groups'(分組+顏色,如 ATC)| 'mapping'(代碼→值對照表)
  builtin: DEFAULT_LAB_TESTS,      // 出廠預設(隨版本更新)
  storageArea: 'sync',             // 'sync'(小,跨機同步)| 'local'(大,見下)
  itemSchema: {...},               // 每筆項目的欄位與驗證規則(匯入時用)
  clinicalImpact: false,           // true = 影響臨床判讀(參考值/單位),UI 需標示
}
```

**項目資料模型——alias 是一等公民**(issue #66/#67 的核心):

```js
// 'list' shape 的單筆項目(示意)
{
  id: 'cbc',                       // 邏輯項目的穩定 id
  label: 'CBC',                    // 顯示名稱(使用者可改)
  codes: ['08011C', '08003C'],     // ⚠️ 一對多:同一項目在不同院所的多個代碼
  enabled: true,                   // 啟用/停用(不刪資料)
  order: 3,                        // 顯示順序(使用者可調)
}
```

「關注項目」是**邏輯概念**(一個 label 對多個 orderCode),不是單一代碼——
比對時任一 code 命中即算該項目。現有程式裡的硬寫特例
(`Overview_LabTests` 的 `isCBCCode()`、`09015C` 的 eGFR/Cr 分支)
就是這個需求的前身,alias 化之後應收斂為資料而非程式分支。

### 儲存分層(硬性約束,先於任何實作;涵蓋 issue #65 的研究結論)

`chrome.storage.sync` 有配額:**單一 key 8KB、總量 100KB**。目前 `atc5Groups` 等
已放 sync,再往裡塞大型對照表會直接寫入失敗。規則:

- **小型自訂**(清單勾選、分組):sync——跨機自動同步,維持現狀。
- **大型對照表**(外部匯入的 mapping,可能數千筆):`chrome.storage.local`
  (5MB,必要時申請 `unlimitedStorage`)。local 不跨機,所以**必須配套
  匯出/匯入 JSON 功能**讓使用者手動搬移與備份。
- settingsSchema 加 `storageArea` 欄位支援此分流(目前全部隱含 sync)。

issue #65 補上的環境約束(**設計前提,不可違反**):

- **不能假設院所能連 Google**:許多院所是封閉網路或未登入 Google 帳號。
  `chrome.storage.sync` 在此情況下 API 仍可用(行為同 local),但**不會**跨機同步——
  所以 Google 同步只能是「可用時的加值」,永遠不可成為必要功能。
- **匯出/匯入 JSON 是主要的可攜與備份機制**(不是大型表專屬的補救措施):
  一鍵匯出全部偏好設定 + 自訂代碼集 → 帶到另一台機器匯入。這同時回應
  #64「各科專屬項目」——匯出檔天然就是**科別範本**,同科同事可直接分享匯入。
- **只存偏好,不存病人資料**:匯出檔與 storage 中的自訂內容僅限設定與代碼集,
  病人資料(dataStore/NHITW_DATA)永不進入設定儲存與匯出檔。

### 合併語意(內建 vs 使用者自訂)

- 內建表是**基底**,使用者自訂是**覆疊(overlay)**:可新增、覆寫、停用單筆,
  但不直接改寫內建資料——這樣版本升級更新內建表時,使用者自訂不會被清掉,
  反之使用者也隨時可「還原此筆/全部還原預設」。
- 存檔格式只存 delta(覆疊部分),不存內建全量——省空間,也讓「內建表升級」
  與「使用者自訂」天然不衝突。

### 外部對照表匯入

- 格式:JSON(必要時支援 CSV 轉換),依代碼集的 `itemSchema` 驗證 → 預覽差異
  (新增幾筆/覆寫幾筆/幾筆無效)→ 使用者確認才寫入。
- **來源標註(provenance)**:匯入的表記錄名稱/來源/匯入日期,設定頁可檢視。
- **臨床安全底線**:`clinicalImpact: true` 的代碼集(參考值、單位對照這類會
  影響判讀的),資料顯示處必須有可辨識的「使用自訂對照」標記,且一鍵還原
  永遠可用。寧可醜,不可讓使用者忘記自己改過參考值。

### 通用編輯器(仿 copyFormat 的成功模式)

一個通用 `CodeSetEditor`(依 `shape` 呈現清單勾選/分組管理/對照表格)+
每代碼集一份 config;取代目前三個各自為政的 dialog。新開一個自訂點的成本
= 一份 config,不再複製整套編輯 UI。

### 與方向一的整合

資料型別描述檔加一欄 `codeSets: ['labFocus', 'labAbbrev', ...]`,
表格管線(方向二)的 columns config 可引用代碼集(例如「只顯示 labFocus
內的代碼」「縮寫欄位查 labAbbrev」),三個方向共用同一批宣告。

## 變數(設定)的處理

已解決,規則見 `Settings.md`。對新資料型別只補一條:**新型別的設定歸入
`defaultSettings.js` 既有 section**(顯示類→`general`、抓取開關→`cloud`、
資料處理→該型別所屬領域 section);只有當設定超過 3–4 個時才開新 section,
開新 section 不需要改 schema(自動衍生)。

## 新 API 資料的決策 checklist(動手前先回答)

1. **抓取**:哪個 imue endpoint?需要 JWT 授權節點嗎?regular 還是 special?
2. **形狀**:回應是 rows、單一物件、還是包裹形?(對應 `responseShape`)
3. **呈現**:獨立 tab、Overview 卡片、還是只進 popup?要不要設定開關(`cloud` section)?
4. **預處理**:純表格(用 toolkit + columns config)還是需要專屬邏輯(寫 processor)?
5. **契約**:要進 `NHITW_DATA` 嗎?`exportKey` 取名一次定終身。
6. **本地匯入**:要支援 JSON 匯入嗎?(`localImportKey`)
7. **測試**:processor 是純函數 → 先寫測試資料與預期輸出,再實作。
8. **自訂性**:使用者需要自訂哪些代碼集?(關注清單/分組/對照表——對應方向五的
   `shape`)自訂資料多大?(決定 sync 或 local)會影響臨床判讀嗎?(`clinicalImpact`)
